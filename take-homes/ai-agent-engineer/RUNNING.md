# Running this solution

## Layout

Following SUBMISSION.md's preferred structure: solution code lives in `solution/` (with
`solution/__init__.py`, as noted there), alongside the original scaffolding and this write-up:

```
take-homes/ai-agent-engineer/
├── harness.py, policy/, conversations/, data/, stubs/frondly_tools.py   <- original, untouched
├── stubs/outbox/*.jsonl, runs/*.json                                    <- generated by your run
├── conftest.py                                                          <- makes solution/ importable for pytest
├── WRITEUP.md, AI_USE.md, RUNNING.md, ARCHITECTURE.md                   <- docs
└── solution/
    ├── __init__.py
    ├── agent.py, policy_engine.py, eval.py
    ├── test_policy_engine.py, test_agent_smoke.py
    └── requirements.txt
```

`harness.py` looks for `agent.py` next to itself first, then falls back to `from solution import
agent` -- this repo uses the fallback, so `agent.py` and `eval.py` both detect they're inside a
`solution/` folder and resolve `stubs/`, `policy/`, and `runs/` one directory up automatically.

## 1. Create the environment (uv, Python 3.11)

```bash
uv venv --python 3.11
```

Activate it:

```bash
# macOS/Linux
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1

# Windows cmd.exe
.venv\Scripts\activate.bat
```

Install dependencies into that venv:

```bash
uv pip install -r solution/requirements.txt
```

## 2. Set OPENAI_API_KEY

This is an environment variable, not a file in the project -- don't put it in any tracked file,
and don't commit it if you're pushing to your fork.

**Windows PowerShell**

```powershell
# current terminal session only
$env:OPENAI_API_KEY = "sk-..."

# persists across future terminals (current one won't see it until you open a new window)
setx OPENAI_API_KEY "sk-..."

# verify
echo $env:OPENAI_API_KEY
```

**Windows cmd.exe**

```cmd
:: current terminal session only
set OPENAI_API_KEY=sk-...

:: persists across future terminals (current one won't see it until you open a new window)
setx OPENAI_API_KEY "sk-..."

:: verify
echo %OPENAI_API_KEY%
```

**macOS/Linux (bash/zsh)**

```bash
export OPENAI_API_KEY=sk-...   # current session only

# persist: add the line above to ~/.bashrc or ~/.zshrc, then reload
echo 'export OPENAI_API_KEY=sk-...' >> ~/.zshrc && source ~/.zshrc
```

Whichever shell you use, set the key in the **same terminal window** you're about to run
`harness.py` from -- a key set with `setx` or added to `~/.zshrc` won't apply to an already-open
terminal until you start a new one.

## 3. Run it

Both commands run from `take-homes/ai-agent-engineer/` (the repo root for this take-home, where
`harness.py` lives) -- not from inside `solution/`:

```bash
python harness.py --repeat 3    # runs all 18 conversations 3x against the real agent
python solution/eval.py         # scores runs/ + stubs/outbox/ -> compliance/helpfulness/stability
```

If you're invoking through `uv` instead of an activated shell:

```bash
uv run python harness.py --repeat 3
uv run python solution/eval.py
```

Model: `gpt-5.6-terra` (OpenAI's balanced cost/capability tier as of July 2026). To try the
flagship instead, change `MODEL` in `solution/agent.py` to `gpt-5.6-sol`, or `gpt-5.5` for the
prior-gen stable option if you'd rather not be on a model that only just went GA.

## 4. Tests (no API key needed)

Run from the repo root (`take-homes/ai-agent-engineer/`) so `conftest.py` is picked up:

```bash
pytest solution/test_policy_engine.py solution/test_agent_smoke.py -v
```

(Running `pytest test_policy_engine.py test_agent_smoke.py -v` from inside `solution/` directly
also works.)

- `test_policy_engine.py` — unit tests for the deterministic guardrails (refund ceiling,
  verification cross-checking, red-flag regex detection).
- `test_agent_smoke.py` — exercises `agent.respond()`'s tool loop with a fake OpenAI client
  (Responses API shape), catching integration bugs without a live model. Every test in this file
  runs against an isolated temp outbox (see its `isolated_outbox` fixture), so running the suite
  never writes into your real `stubs/outbox/` -- one test exercises a real `create_escalation`
  call end-to-end, and without that isolation it would otherwise leave test entries in the
  outbox you're submitting as graded evidence.
